## 1. Философия и математическая модель AMA

### 1.1. Мотивация и инженерная философия

Управление памятью в системных и высоконагруженных языках программирования традиционно сводилось к выбору между тремя компромиссами:

1. **Ручное управление памятью (C, C++, Zig):** максимальная предсказуемость и производительность, но отсутствие статических гарантий безопасности приводит к уязвимостям класса Use-After-Free (UAF), Double Free, Buffer Overflow, Dangling Pointers и Data Races.
2. **Трассирующая сборка мусора (Go, Java, C#):** низкий когнитивный порог, но непредсказуемые задержки (Stop-The-World / GC Pauses), двукратный-трёхкратный перерасход оперативной памяти для поддержания низкой частоты сборок, накладные расходы на барьеры записи (Write Barriers) и отсутствие детерминированных деструкторов (RAII).
3. **Аффинная система типов с явным параметрическим полиморфизмом времён жизни (Rust Borrow Checker):** нулевые накладные расходы в рантайме, но необходимость ручной разметки сигнатур времён жизни (`<'a, 'b: 'a>`), каскадное распространение аннотаций по типам структур и высокая сложность построения графовых или аренных структур данных без `unsafe`.

**APS Adaptive Memory Architecture (AMA)** предлагает четвёртый путь: **статически верифицируемую иерархическую модель владения и прав доступа второго класса (Second-Class Access Capabilities) в сочетании со встроенными лексическими регионами памяти (`region`) и автоматическим вычислением точек освобождения (Compile-Time Free Placement — CTFP)**.

Ключевые постулаты AMA:
- **Ноль сборщика мусора (Zero GC):** в рантайме APS нет фонового трассировщика, фаз маркировки или барьеров записи.
- **Ноль ручных вызовов `free()` / `delete`:** программист никогда не освобождает память вручную в безопасном коде; точки освобождения вычисляются компилятором на графе потока управления (MIR CFG).
- **Ноль явных аннотаций `'a` в обычном коде:** ссылки представлены как права доступа второго класса (`read T`, `write T`), которые не могут храниться в произвольных кучных структурах вне лексических скоупов и регионов, что позволяет компилятору выводить зависимости времени жизни полностью автоматически.
- **Свобода выбора модели размещения:** каждый объект автоматически или декларативно попадает на один из четырёх уровней памяти, оптимальных для его паттерна использования.

### 1.2. Сравнительная характеристика моделей памяти

| Характеристика | Ручное (C/C++) | Garbage Collector (Go/Java) | Rust Borrow Checker | **APS AMA** |
| :--- | :--- | :--- | :--- | :--- |
| Защита от Use-After-Free / Double Free | Нет | В рантайме (GC) | Статическая | **Статическая (OLG + CTFP)** |
| Защита от Data Races | Нет | Нет (гонки ссылок возможны) | Статическая (`Send`/`Sync`) | **Статическая (`read`/`write`/`shared`)** |
| Паузы сборщика мусора | 0 мс | 0.5–100+ мс | 0 мс | **0 мс (детерминированный CTFP)** |
| Ручные метки жизни `'a` в сигнатурах | Нет | Нет | Обязательны в сложных случаях | **Не требуются (Capabilities 2-го класса)** |
| Графы и циклические структуры | Сырые указатели (опасно) | Нативно (через GC-кучу) | Сложно (`Rc<RefCell>` / `unsafe`) | **Нативно (`region` + `RegionHandle<T>`)** |
| Групповое освобождение арен $O(1)$ | Ручные аллокаторы (без проверки) | Нет | Сторонние крейты со сложными `'a` | **Встроено в язык (`region name { ... }`)** |

### 1.3. Формальная математическая модель AMA

Абстрактная машина памяти AMA на этапе статического анализа MIR определяется семиэлементным кортежем состояния:

$$\Sigma = (\mathcal{S}, \mathcal{H}, \mathcal{R}, \mathcal{Sh}, \mathcal{G}, \Gamma, \Delta)$$

где:
- $\mathcal{S} : \text{VarId} \rightharpoonup \text{Slot}$ — отображение идентификаторов локальных переменных стекового кадра в слоты памяти.
- $\mathcal{H} : \text{AllocId} \rightharpoonup \text{HeapObject}$ — множество объектов одиночного владения на куче (`Managed Ownership Tier`).
- $\mathcal{R} = \{ r_1, r_2, \dots, r_k \}$ — стек активных лексических регионов памяти, упорядоченный по отношению строгого вложения времени жизни $r_k \sqsubset r_{k-1} \sqsubset \dots \sqsubset r_1$.
- $\mathcal{Sh} : \text{SharedId} \rightharpoonup (\text{ImmutableValue}, \text{AtomicRefCount})$ — пространство глубоко неизменяемых разделяемых объектов (`Shared Immutable Tier`).
- $\mathcal{G} = (V, E_{\text{own}}, E_{\text{borrow}})$ — ориентированный граф владения и заимствования (**Ownership & Liveness Graph, OLG**).
- $\Gamma : \text{Place} \to (\text{Type}, \text{InitState}, \text{RegionTag})$ — среда типизации и состояния инициализации для каждого пути доступа (`Place`, например `x`, `x.field`, `x.arr[i]`).
- $\Delta : \text{Place} \to \mathcal{P}(\text{Loan})$ — множество активных заимствований (прав доступа `read` и `write`) в текущей программной точке $p \in \text{CFG}$.

#### Инвариант 1 (Единственность владельца и ацикличность)
Для любого объекта $o \in \mathcal{H}$ в любой достижимой программной точке $p$ полустепень захода по рёбрам владения $E_{\text{own}}$ равна единице, а подграф $(V, E_{\text{own}})$ является лесом корневых ориентированных деревьев (DAG без разделяемых вершин):

$$\forall o \in \mathcal{H}: \quad \text{in-deg}_{E_{\text{own}}}(o) = 1 \quad \land \quad (V, E_{\text{own}}) \text{ не содержит циклов}$$

#### Инвариант 2 (Aliasing XOR Mutability для прав доступа)
Для любого пути памяти $\pi \in \text{Place}$ и любого его префикса или суффикса $\pi' \in \text{Overlap}(\pi)$ в программной точке $p$ число активных прав на запись $W(\pi, p)$ и число активных прав на чтение $R(\pi, p)$ подчиняются закону:

$$\forall \pi \in \text{Place}, \forall p \in \text{CFG}: \quad \big(W(\pi, p) = 1 \land R(\pi, p) = 0\big) \;\lor\; \big(W(\pi, p) = 0 \land R(\pi, p) \ge 0\big)$$

При этом два пути $\pi_1 = x.f_1$ и $\pi_2 = x.f_2$ при $f_1 \neq f_2$ считаются **ортогональными (дизъюнктными)**: $\pi_1 \notin \text{Overlap}(\pi_2)$, что формально разрешает $W(x.f_1, p) = 1 \land W(x.f_2, p) = 1$.

#### Инвариант 3 (Строгое подчинение времени жизни заимствования и региона)
Для любого заимствования $\ell = (\text{cap}, \pi_{\text{src}}, \pi_{\text{dst}})$, созданного из источника $\pi_{\text{src}}$ в регионе $r_{\text{src}}$, область жизни заимствования $\mathcal{L}(\ell)$ строго вложена в область жизни владельца $\mathcal{L}(\pi_{\text{src}})$ и в область жизни региона $r_{\text{src}}$:

$$\mathcal{L}(\ell) \subseteq \mathcal{L}(\pi_{\text{src}}) \subseteq \mathcal{L}(r_{\text{src}})$$

## 2. Четыре уровня памяти AMA

Архитектура AMA делит адресное пространство программы на четыре специализированных уровня (Tiers). Компилятор автоматически выбирает между Уровнем 1 и Уровнем 2, а программист может явно задействовать Уровень 3 (`region`) и Уровень 4 (`shared`).

```
+-----------------------------------------------------------------------------------+
|                        APS ADAPTIVE MEMORY ARCHITECTURE                           |
+-----------------------------------------------------------------------------------+
| Уровень 1: Local Memory (Stack Tier)                                              |
| - Примитивы, структуры, не избегающие кадра функции (Escape Analysis)             |
| - Аллокация: O(1) сдвиг RSP | Освобождение: O(1) эпилог функции                   |
+-----------------------------------------------------------------------------------+
| Уровень 2: Managed Ownership (Single-Owner Heap Tier)                             |
| - Динамические буферы (String, Vec<T>, Map<K,V>, Box<T>), избегающие объекты      |
| - Аллокация: системный/APS аллокатор | Освобождение: детерминированный CTFP       |
+-----------------------------------------------------------------------------------+
| Уровень 3: Region Memory (Lexical Arena Tier: `region name { ... }`)              |
| - Парсеры, AST, графы, пакетная обработка запросов, циклические структуры         |
| - Аллокация: O(1) bump-pointer | Освобождение: O(1) сброс всей арены на выходе    |
+-----------------------------------------------------------------------------------+
| Уровень 4: Shared Immutable Memory (`Shared<T>` / `share(val)`)                   |
| - Конфигурации, кэши, справочники, сообщения между потоками и async-задачами      |
| - Аллокация: куча + атомарный счётчик | Освобождение: при падении счётчика в 0    |
+-----------------------------------------------------------------------------------+
```

### 2.1. Уровень 1: Local Memory (Stack Tier и Escape Analysis)

На первом уровне размещаются все локальные переменные примитивных типов (`i8..i64`, `u8..u64`, `f32`, `f64`, `bool`, `char`), кортежи и пользовательские структуры `struct` и перечисления `enum` фиксированного размера (`Sized`), а также динамические агрегаты, для которых проход **AMA Escape Analysis** доказал, что они не покидают пределы текущей функции.

**Формальный критерий неизбегания (Non-Escaping Criterion):**
Объект $o$, созданный в функции $F$, считается неизбегающим ($\text{Escapes}(o, F) = \text{false}$), если одновременно выполняются четыре условия:
1. $o$ не возвращается из $F$ по значению (`return o`) и не входит в состав возвращаемой структуры.
2. $o$ не передаётся с правом `take` в функцию $G$, которая не подлежит встраиванию (inlining) или сама сохраняет параметр во внешнем состоянии.
3. Ссылка или дескриптор на $o$ не записывается в изменяемый параметр `write Param` внешней функции.
4. $o$ не передаётся в асинхронную задачу, переживающую текущий стек-кадр, или в отсоединяемый поток.

Если $\text{Escapes}(o, F) = \text{false}$ и размер $\text{sizeof}(o) \le \text{STACK\_PROMOTION\_THRESHOLD}$ (по умолчанию 4096 байт), компилятор применяет:
- **Stack Allocation Promotion:** буфер размещается непосредственно в стековом кадре функции (`alloca` в LLVM IR).
- **Scalar Replacement of Aggregates (SROA):** поля структуры раскладываются по регистрам процессора без обращения к оперативной памяти.

### 2.2. Уровень 2: Managed Ownership (Single-Owner Heap Tier и CTFP)

Второй уровень обслуживает динамические структуры данных с изменяемым размером (`String`, `Vec<T>`, `HashMap<K, V>`, `Box<T>`) и объекты, которые передаются вверх по стеку вызовов (`return`) или перемещаются между владельцами (`take`).

- У каждого объекта на этом уровне в каждый момент времени существует **ровно один владелец** (`own T`).
- При выходе владельца из области видимости или после его последнего использования (если владелец не был перемещён дальше через `take` или `return`) проход **Compile-Time Free Placement (CTFP)** автоматически вставляет в MIR инструкцию деструктора `DropAndFree(place)`.
- Никакого подсчёта ссылок (`refcount`) и никаких заголовков сборщика мусора у объектов Уровня 2 нет: указатель в памяти указывает непосредственно на полезные данные (Zero Metadata Overhead).

### 2.3. Уровень 3: Region Memory (`region` Tier)

Третий уровень предназначен для высокопроизводительной пакетной аллокации и построения сложных связанных структур данных (деревья разбора, компиляторные IR, графы с циклами, обработка HTTP/RPC-запросов).

Синтаксис объявления региона:
```aps
region scratch {
    var node_a = scratch.alloc(Node { id: 1, next: None })
    var node_b = scratch.alloc(Node { id: 2, next: Some(node_a) })
    process_nodes(read node_b)
} // <- Мгновенное освобождение всей памяти региона `scratch` за O(1)
```

**Архитектура и инварианты региона:**
1. **Аллокация за $O(1)$ (Bump-Pointer Allocation):** регион управляет линейным сегментом виртуальной памяти (или цепочкой страниц по 64 КБ). Выделение памяти под объект размера $S$ с выравниванием $A$ сводится к вычислению:
   $$\text{ptr} = \text{align\_up}(\text{cursor}, A), \quad \text{cursor}' = \text{ptr} + S$$
   Это занимает 2–3 машинные инструкции без вызовов системного аллокатора и без блокировок (lock-free, так как регион привязан к текущему потоку).
2. **Освобождение за $O(1)$ (Bulk Deallocation):** при выходе из лексического блока `region name { ... }` (включая выход по `return`, `break`, `?` или панике) вызываются деструкторы внешних ресурсов (например, файловых дескрипторов, если они были зарегистрированы в регионе), после чего указатель вершины арены сбрасывается в начало за одну операцию. Индивидуальные вызовы `free()` для тысяч мелких объектов полностью устраняются.
3. **Инвариант невыхода ссылок (No-Escape Invariant — ошибка `E0305`):**
   Каждому блоку `region r` компилятор присваивает уникальный фантомный тег региона $\rho_r$. Любая ссылка или дескриптор `RegionHandle<T, r>`, аллоцированный в регионе $r$, помечается тегом $\rho_r$. Запрещается:
   - возвращать значение, содержащее тег $\rho_r$, из блока `region r`;
   - записывать значение с тегом $\rho_r$ в переменную, объявленную во внешней области видимости ($r_{\text{outer}} \sqsupset r$).

### 2.4. Уровень 4: Shared Immutable Memory (`shared T` / `Shared<T>`)

Четвёртый уровень решает задачу безопасного разделения данных между множеством владельцев, потоков ОС и асинхронных задач.

- Создание разделяемого объекта выполняется встроенным оператором заморозки `share(expr)` или конструктором `Shared::new(take value)`.
- При вызове `share(val)`:
  1. Исходный владелец `val` передаёт владение (`take`) в блок памяти Уровня 4.
  2. Тип значения преобразуется в `Shared<T>` (или краткую форму `shared T`).
  3. Объект и все его транзитивно достижимые поля становятся **глубоко неизменяемыми (Deeply Immutable)**. Любая попытка получить `write`-доступ к полю внутри `shared T` отвергается компилятором на этапе проверки прав доступа (`E0043`).
- Копирование дескриптора `Shared<T>` (`.clone()` или передача в поток) выполняет атомарный инкремент счётчика ссылок (`fetch_add(1, Relaxed)`).
- Поскольку объект гарантированно неизменяем после заморозки, произвольное число потоков может читать его одновременно без мьютексов, блокировок и риска гонок данных (Data Races невозможны по построению).

## 3. Понятие владельца объекта (`own T`) и граф владения (OLG)

### 3.1. Владение по умолчанию

В языке APS любое выражение, создающее значение, и любая переменная без модификатора права доступа (`read` / `write`) является **полноправным владельцем (`own T`)**:

```aps
let config: AppConfig = load_config() // `config` имеет квалификацию `own AppConfig`
var buffer = ByteBuffer::with_capacity(4096) // `buffer` — единственный владелец буфера
```

Ключевое слово `own` является квалификатором по умолчанию для полей структур, локальных переменных и возвращаемых значений функций и может опускаться в поверхностном синтаксисе (`T` эквивалентно `own T`).

### 3.2. Решётка состояний переменной (Initialization & Ownership Lattice)

Анализатор AMA сопоставляет каждому пути памяти (`Place`) состояние из конечной решётки $\mathcal{L}_{\text{state}}$:

```
                 +-------------------+
                 |   Uninitialized   |
                 +---------+---------+
                           | (присваивание начального значения)
                           v
                 +-------------------+
      +--------->|    Owned(Valid)   |<---------+
      |          +----+----+----+----+          |
      |               |    |    |               |
(окончание            |    |    |         (окончание
 read-заимств.)       |    |    |          write-заимств.)
      |               |    |    |               |
      |   +-----------+    |    +-----------+   |
      |   | (read)         | (take/move)    |   | (write)
      |   v                |                v   |
+-----+---------------+    |    +---------------+-----+
|  BorrowedRead(n>=1) |    |    |    BorrowedWrite    |
+---------------------+    |    +---------------------+
                           v
            +--------------+--------------+
            |                             |
            v                             v
+-----------------------+     +-----------------------+
| PartiallyMoved(Mask)  |     |         Moved         |
+-----------+-----------+     +-----------+-----------+
            |                             |
            +--------------+--------------+
                           | (повторная полная инициализация `var`
                           |  или выход из области видимости)
                           v
                 +-------------------+
                 |       Freed       |
                 +-------------------+
```

Правила переходов на точках слияния потока управления (Join Points в CFG, например после `if/else` или `match`):
- Если в ветке `then` переменная `x` имеет состояние `Owned(Valid)`, а в ветке `else` — состояние `Moved`, то в точке слияния переменная переходит в состояние `MaybeMoved`.
- Для переменной в состоянии `MaybeMoved`:
  - запрещено любое чтение (`read`), модификация (`write`) или повторное перемещение (`take`) — ошибка `E0202`;
  - компилятор автоматически генерирует скрытый булев флаг на стеке (`drop_flag_x: bool`), чтобы при выходе из функции освободить `x` только в том случае, если выполнение прошло по ветке, где `x` остался `Owned(Valid)`.

### 3.3. Построение графа владения и живучести (OLG)

Проход анализатора AMA на уровне MIR строит **Ownership & Liveness Graph (OLG)** в три фазы:
1. **Def-Use & Liveness Analysis (Обратный потоковый анализ):** для каждой переменной $v$ и каждого поля $v.f$ вычисляется множество программных точек $\text{Live}(v) \subseteq \text{CFG}$, в которых значение $v$ будет прочитано или модифицировано в будущем.
2. **Loan Propagation (Прямой потоковый анализ):** вычисляются интервалы активности каждого заимствования `read` и `write` по принципу **Non-Lexical Lifetimes (NLL)** — заимствование завершается сразу после *последнего фактического использования* ссылки в CFG, а не обязательно в конце фигурной скобки `{ ... }`.
3. **CTFP Injection:** в точках, где $v \notin \text{Live}_{\text{out}}(p)$ и $\text{State}(v) = \text{Owned(Valid)}$, вставляется вызов деструктора.

## 4. Анализ времени жизни (Lifetime Analysis) без ручных аннотаций

### 4.1. Почему в APS нет `'a` в обычном коде

В Rust необходимость явных параметров времени жизни `'a` возникает по двум причинам:
1. Ссылки `&'a T` являются типами первого класса (First-Class Types), которые можно сохранять внутри произвольных структур на куче, векторов и глобальных контейнеров.
2. Компилятор Rust намеренно не выводит связь времён жизни между входами и выходом функции, требуя сигнатур вида `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str`.

В APS принята модель **прав доступа второго класса (Second-Class Access Capabilities)** в сочетании с **выводом множества источников (Provenance Set Inference)**:
1. Права `read T` и `write T` могут существовать только в параметрах функций, локальных привязках внутри тела функции и возвращаемых представлениях (Views/Slices). Поля обычных структур на Уровне 2 обязаны владеть своими данными (`own T` или `Shared<T>`), а ссылочные графы строятся внутри `region` через `RegionHandle<T>`.
2. Для функций, возвращающих ссылочное представление (`Slice<T>`, `str`, `read T`), компилятор автоматически вычисляет **множество происхождения результата** $\text{Origin}(\text{ret})$:

$$\text{Origin}(\text{ret}) \subseteq \{ p_i \mid p_i \text{ — входной параметр с правом } \text{read} \text{ или } \text{write} \}$$

### 4.2. Алгоритм вывода времени жизни возвращаемых представлений

Пусть функция имеет сигнатуру:
```aps
fn select_slice(read primary: String, read fallback: String, use_primary: bool) -> read str
```
1. Если анализатор тела функции видит, что возвращаемое значение может происходить как из `primary`, так и из `fallback`, он автоматически приписывает результату множество источников $\text{Origin}(\text{ret}) = \{ \text{primary}, \text{fallback} \}$.
2. На стороне вызывающего кода (`Call Site`):
   ```aps
   var a = String::from("alpha")
   var b = String::from("beta")
   let view = select_slice(read a, read b, true)
   ```
   время жизни `view` связывается с пересечением времён жизни аргументов:
   $$\mathcal{L}(\text{view}) \subseteq \mathcal{L}(a) \cap \mathcal{L}(b)$$
   До тех пор, пока `view` используется (жив по NLL), оба объекта `a` и `b` находятся в состоянии `BorrowedRead` и защищены от модификации (`write`) и перемещения (`take`). Как только `view` перестаёт использоваться, блокировка с `a` и `b` автоматически снимается.

## 5. Семантика прав доступа (Access Capabilities: `read`, `write`, `take`)

Передача любого не-примитивного значения в функцию в APS требует явного согласования права доступа в сигнатуре функции и в точке вызова. Это делает код полностью прозрачным при чтении: глядя на вызов функции, инженер мгновенно видит, может ли функция изменить объект или забрать владение им.

### 5.1. Сводная таблица прав доступа

| Право доступа | Синтаксис параметра | Синтаксис вызова | Чтение | Запись | Перемещение (`Move`) | Допустимые одновременные алиасы | Кто освобождает память |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Чтение (`read`)** | `name: read T` (или `read name: T`) | `read expr` (или авто для `read`-методов) | Да | **Запрещено (`E0042`)** | **Запрещено (`E0044`)** | Неограниченное число других `read T` | Вызывающая сторона (Caller) |
| **Запись (`write`)** | `name: write T` (или `write name: T`) | `write expr` (требует `var`) | Да | **Да** | Запрещено без замены значения | **Ноль** (полная эксклюзивность `E0040`/`E0041`) | Вызывающая сторона (Caller) |
| **Захват (`take`)** | `name: take T` (или `take name: T`) | `take expr` | Да | Да (если `var`) | **Да (полная передача владения)** | Источник переходит в `Moved` (`E0201`/`E0301`) | Вызываемая функция (Callee) |

> **Примечание о синтаксической эквивалентности в APS:**
> В заголовках функций допускается как префиксная запись `fn process(read user: Account, write log: AuditLog, take packet: Packet)`, так и постфиксная запись в позиции типа `fn process(user: read Account, log: write AuditLog, packet: take Packet)`. Обе формы порождают идентичный узел AST `ParamCapability::{Read, Write, Take}`.

### 5.2. Право `read T` (Shared Immutable Capability)

1. Предоставляет вызываемой функции временный невладеющий доступ только для чтения.
2. Можно получить из любой инициализированной переменной (`let` или `var`), а также из существующего `read T`, `write T` (через понижение права — Capability Downgrade / Reborrow) или `Shared<T>`.
3. Любая попытка изменить поле объекта через `read T` (например, `driver.balance += 100`) или вызвать для него мутирующий метод (`write self`) приводит к ошибке компиляции **`E0042: cannot modify a read-only value`**.
4. Пока активно хотя бы одно заимствование `read x`, запрещено создавать `write x` (`E0040`) и запрещено перемещать `take x` (`E0203`).

### 5.3. Право `write T` (Exclusive Mutable Capability)

1. Предоставляет эксклюзивный временный доступ для чтения и модификации объекта на месте (in-place mutation).
2. Может быть получено **только** из переменной, объявленной как изменяемая (`var`), либо путём повторного заимствования (reborrowing) из активного параметра `write T`. Попытка взять `write` от неизменяемой привязки `let` вызывает ошибку **`E0045: cannot borrow immutable binding as writable`**.
3. На время активности `write x` действует строгая эксклюзивность: ни один другой путь не может читать (`read x`), модифицировать (`write x`) или перемещать (`take x`) этот объект.
4. **Замена значения по `write`:** внутри функции, получившей `write target: T`, разрешено полное перезаписывание `*target = new_value`. При этом старое значение детерминированно уничтожается перед записью нового, поэтому вызывающая сторона всегда остаётся с валидным инициализированным объектом.

### 5.4. Раздельный доступ к полям (Field-Disjoint Projection)

Анализатор AMA отслеживает заимствования не на уровне всей переменной целиком, а на уровне **путей проекции полей (`Place Projection`: `x.a.b`)**.

Если структура `EngineState` имеет поля `telemetry: Telemetry` и `actuators: Actuators`, то пути `state.telemetry` и `state.actuators` не пересекаются. Следовательно, компилятор APS **разрешает** одновременную передачу разных полей одной структуры с правом `write`:

```aps
var state = EngineState::new()
// Корректно: пути `state.telemetry` и `state.actuators` дизъюнктны!
calibrate_step(read state.telemetry, write state.actuators)
```

Однако для индексации динамических коллекций (`vec[i]` и `vec[j]`), где равенство индексов $i = j$ невозможно доказать статически в общем случае, анализатор рассматривает весь контейнер `vec[..]` как единый путь памяти. Для одновременного мутабельного доступа к двум непересекающимся срезам предоставляется проверенный метод стандартной библиотеки `vec.split_at_write(mid)`.

### 5.5. Право `take T` (Ownership Transfer Capability)

1. Передаёт полное владение объектом от вызывающей стороны (Caller) к вызываемой функции (Callee).
2. На стороне вызова обязательно явное ключевое слово `take`: `consume_buffer(take buf)`. Это исключает случайную потерю владения при обычном вызове функции.
3. Сразу после вычисления аргумента `take buf` переменная `buf` в вызывающей функции переходит в состояние `Moved`. Любое последующее обращение к `buf` (без предварительного присваивания нового значения, если `buf` объявлен как `var`) пресекается компилятором с кодом ошибки **`E0201` / `E0301` (`use of moved value`)**.
4. Ответственность за освобождение памяти объекта полностью переходит к вызываемой функции.

## 6. Семантика перемещения (Move) и копирования (`Copy`)

Все типы данных в APS делятся на два фундаментальных класса по семантике присваивания и передачи по значению:

### 6.1. Типы с семантикой копирования (`Copy` Types)

К категории `Copy` относятся типы, значения которых целиком размещаются на стеке/в регистрах, не владеют ресурсами кучи или ОС и могут быть продублированы простым побитовым копированием (`memcpy`) без нарушения инвариантов владения:
- Целые числа со знаком: `i8`, `i16`, `i32`, `i64`, `isize`.
- Целые числа без знака: `u8`, `u16`, `u32`, `u64`, `usize`.
- Числа с плавающей точкой IEEE 754: `f32`, `f64`.
- Логический тип `bool` и скалярное значение Unicode `char` (32 бита).
- Неизменяемые срезы только для чтения и ссылки внутри выражения.
- Пользовательские структуры `struct` и перечисления `enum`, все поля которых реализуют `Copy` и для которых явно указан атрибут `@derive(Copy)` (или `struct Point is Copy`).

Для типов `Copy` операция `let y = x` или передача `x` в функцию создаёт независимую побитовую копию, а исходная переменная `x` остаётся в состоянии `Owned(Valid)`.

### 6.2. Типы с семантикой перемещения (`Move` / Resource Types)

Любой тип, владеющий динамической памятью (`String`, `Vec<T>`, `Map<K, V>`, `Box<T>`), дескриптором ОС (`File`, `TcpStream`, `Mutex<T>`) или не помеченный как `Copy`, подчиняется **аффинной семантике перемещения (Move Semantics)**:
1. Присваивание `let dest = take src` (или `let dest = src`) копирует только стековый заголовок (например, 24 байта `(ptr, len, cap)` для `Vec<T>`) за $O(1)$ без клонирования буфера в куче.
2. Источник `src` немедленно помечается в OLG как `Moved`.
3. Деструктор для `src` подавляется, а единственным ответственным за освобождение кучного буфера становится `dest`.
4. Если программисту действительно нужна глубокая копия буфера в куче, он обязан явно вызвать метод `.clone()`: `let copy = src.clone()`. В APS **запрещены неявные дорогостоящие копирования (No Implicit Copy Constructors)**.

## 7. Детерминированное освобождение памяти (CTFP) и порядок деструкторов

### 7.1. Строгий порядок освобождения (LIFO)

Алгоритм **Compile-Time Free Placement (CTFP)** гарантирует 100% предсказуемый, воспроизводимый порядок вызова деструкторов (`drop`) и освобождения памяти:

1. **Локальные переменные блока `{ ... }`:** освобождаются на выходе из области видимости (или в точке завершения живучести, если у типа нет наблюдаемых побочных эффектов в `drop`) в **строго обратном порядке их объявления (Last-In, First-Out — LIFO)**.
   ```aps
   fn process() {
       let db = Database::connect()   // Объвлен 1-м -> Освободится 3-м
       let tx = Transaction::begin()  // Объявлен 2-м -> Освободится 2-м
       let buf = Buffer::allocate()   // Объявлен 3-м -> Освободится 1-м
   }
   ```
2. **Поля структур (`struct`) и варианты перечислений (`enum`):** при уничтожении составного объекта сначала выполняется пользовательский метод `fn drop(write self)` (если он определён для типа), после чего поля структуры рекурсивно освобождаются в **обратном порядке их объявления** в определении `struct`.
3. **Элементы коллекций (`Vec<T>`, `[T; N]`):** элементы уничтожаются последовательно от последнего индекса к нулевому, после чего освобождается сам буфер памяти в куче.
4. **Временные выражения (Temporaries):** временные объекты, созданные внутри составного выражения (например, `print(format_report(load_data()))`), уничтожаются немедленно на границе содержащей инструкции (statement boundary) в обратном порядке создания.

### 7.2. Освобождение на всех путях графа потока управления (CFG)

Компилятор строит полный граф потока управления в MIR и верифицирует, что на каждом ребре выхода из блока (`NormalExit`, `EarlyReturn`, `TryErrorPropagation (?)`, `Break`, `Continue`, `PanicUnwind`) все живые локальные владельцы корректно освобождаются:
- При раннем `return expr`: сначала вычисляется `expr` (и если это перемещение локальной переменной `x`, то `x` переходит в `Moved`), затем в порядке LIFO вызываются деструкторы всех оставшихся в состоянии `Owned(Valid)` переменных всех охватывающих блоков функции, и лишь затем управление передаётся вызывающей функции.
- При условном перемещении (когда переменная `x` перемещена через `take x` только внутри одной ветки `if`): компилятор аллоцирует на стеке 1-байтовый флаг инициализации `drop_flag_x`, устанавливает его в `true` при инициализации, сбрасывает в `false` при перемещении и проверяет перед вызовом `free(x)` в эпилоге функции.

## 8. Циклические структуры данных, `RegionHandle<T>` и `Weak<T>`

Согласно архитектурному решению **ADR-004**, одиночное владение Уровня 2 (`own T`) образует строго ориентированный ациклический граф (DAG). Попытка замкнуть цикл через `own T` невозможна статически, а наивное замыкание цикла через подсчёт ссылок привело бы к утечке памяти.

Для безопасного и эффективного представления произвольных графов, двусвязных списков, деревьев с указателями на родителя (`parent`) и циклических структур в APS предусмотрены два канонических механизма:

### 8.1. Механизм 1: Регионы памяти с типизированными дескрипторами (`region` + `RegionHandle<T>`)

Это основной, наиболее быстрый и дружественный к кэшу процессора способ работы с графами в APS:

```aps
struct GraphNode {
    id: u32,
    edges: Vec<RegionHandle<GraphNode>>
}

fn run_graph_algorithm() {
    region arena {
        var n1 = arena.alloc(GraphNode { id: 1, edges: Vec::new() })
        var n2 = arena.alloc(GraphNode { id: 2, edges: Vec::new() })

        // Формируем взаимный цикл между n1 и n2 внутри региона:
        arena.get_write(n1).edges.push(n2)
        arena.get_write(n2).edges.push(n1)

        let start_id = arena.get_read(n1).id
    } // Вся память узлов n1 и n2 мгновенно освобождается вместе с регионом `arena`!
      // Никаких утечек памяти несмотря на цикл между n1 и n2!
}
```

**Свойства `RegionHandle<T>`:**
- `RegionHandle<T>` представляет собой легковесный типизированный дескриптор (индекс/смещение в регионе, маркированный фантомным идентификатором региона на этапе компиляции), реализующий семантику `Copy`.
- Доступ к данным узла осуществляется через регион: `arena.get_read(handle)` (возвращает `read T`) или `arena.get_write(handle)` (возвращает `write T`).
- Попытка использовать `handle` одного региона с другим регионом или вынести `handle` за пределы блока `region arena` блокируется на этапе компиляции ошибкой **`E0305`** или **`E0306` (`region handle mismatch`)**.

### 8.2. Механизм 2: Разделяемые указатели и слабые ссылки (`Shared<T>` и `Weak<T>`)

Если узлы структуры должны жить независимо от лексического региона и освобождаться поштучно по мере устаревания (например, долгоживущий кэш сессий или дерево подписок), используется пара `Shared<T>` (сильная ссылка, удерживающая объект) и `Weak<T>` (слабая ссылка, не препятствующая освобождению объекта):

- Прямые связи (от родителя к потомку) хранят `Shared<Node>`.
- Обратные связи (от потомка к родителю или перекрёстные ссылки) хранят `Weak<Node>`, созданный вызовом `Shared::downgrade(read parent)`.
- Для чтения данных через `Weak<T>` программист обязан вызвать `weak_ref.upgrade()`, который атомарно проверяет, жив ли объект, и возвращает `Option<Shared<T>>` (`Some(shared_node)` или `None`, если родитель уже освобождён). Висячие указатели исключены на 100%.

## 9. Асинхронное время жизни и структурный параллелизм (`task_scope`)

Асинхронное программирование (`async` / `await`) в традиционных языках часто вступает в конфликт с безопасностью памяти: если асинхронная задача (`Task`) может пережить функцию, которая её породила, передача в задачу локальных ссылок `read T` или `write T` приводит к Use-After-Free стекового кадра.

APS решает эту проблему на уровне языка через **структурный параллелизм (`task_scope`)**:

### 9.1. Гарантии `task_scope`

```aps
async fn process_chunks(read header: PacketHeader, write left: Slice<u8>, write right: Slice<u8>) {
    await task_scope |scope| {
        // Обе задачи гарантированно завершатся ДО выхода из блока `task_scope`!
        scope.spawn(async {
            transform_chunk(read header, write left)
        })
        scope.spawn(async {
            transform_chunk(read header, write right)
        })
    } // Неявная точка барьерной синхронизации (join всех порождённых задач)
}
```

**Инварианты AMA для `task_scope`:**
1. Блок `task_scope` не может завершиться, пока все порождённые внутри него через `scope.spawn(...)` дочерние задачи не завершат выполнение (даже в случае ошибки или отмены).
2. Благодаря этому барьеру задачи внутри `scope.spawn` имеют право безопасно захватывать локальные переменные родительской функции по `read T` (для любого числа задач одновременно) и по `write T` (при условии, что каждая задача захватывает дизъюнктный путь памяти — иначе ошибка **`E0402: concurrent mutable borrow across tasks`**).
3. Если же программист запускает глобальную отсоединённую задачу через `async::spawn_detached(...)`, которая может пережить текущую функцию, анализатор AMA **запрещает** захват любых `read` и `write` ссылок (`E0401: borrowed value does not live long enough for detached task`) и разрешает передавать данные только через `take` (перемещение владения) или `Shared<T>`.

## 10. Потокобезопасность (Thread Safety: инварианты `Send` и `Sync`)

Анализатор AMA (проход **AMA Concurrency Pass**) статически гарантирует полное отсутствие гонок данных (**Data-Race Freedom**) в многопоточных программах.

### 10.1. Автоматические маркерные свойства `Send` и `Sync`

Компилятор автоматически выводит для каждого типа два фундаментальных свойства:
1. **`Send` (Безопасность перемещения между потоками):** тип `T` является `Send`, если передача владения `take T` из потока $A$ в поток $B$ безопасна.
   - `Send` реализуют все примитивы, структуры из `Send`-полей, `own T` (коллекции, строки, буферы), `Shared<T>`, `Mutex<T>`, `ChannelSender<T>`.
   - **НЕ являются `Send`:** неатомарные дескрипторы регионов `RegionHandle<T>` (поскольку аллокатор региона локален для потока — `E0404`), сырые указатели `*const T` / `*mut T` и привязанные к потоку дескрипторы ОС (`ThreadLocalHandle`).
2. **`Sync` (Безопасность одновременного чтения из разных потоков):** тип `T` является `Sync`, если одновременная передача `read T` в несколько потоков (например, внутри `thread::scope` или `task_scope`, либо внутри `Shared<T>`) не может вызвать гонку данных.
   - `Sync` реализуют все неизменяемые примитивы, `Shared<T>`, атомарные типы (`AtomicI64`, `AtomicBool`) и синхронизационные примитивы (`Mutex<T>`, `RwLock<T>`).

### 10.2. Правила межпоточного взаимодействия

- Передача несинхронизированного права `write T` одновременно в два потока или захват изменяемой переменной `var x` без `take` или `Mutex` из нескольких потоков отвергается с ошибкой **`E0403: cannot share mutable state between threads without synchronization`**.
- Для изменяемого разделяемого состояния между потоками программист обязан использовать либо передачу сообщений по каналам (`std::sync::Channel<T>` с передачей владения `take msg`), либо `Shared<Mutex<T>>` / `Shared<RwLock<T>>`. При вызове `mutex.lock()` возвращается охранный объект `MutexGuard<T>`, предоставляющий эксклюзивное право `write T` строго на время удержания блокировки; попытка сохранить ссылку на данные вне области жизни `MutexGuard` блокируется ошибкой времени жизни **`E0304`**.

## 11. Границы безопасности FFI (`unsafe` и `extern "C"`)

Взаимодействие с внешними библиотеками на C/C++ или системными вызовами ОС осуществляется через интерфейс внешних функций (`extern "C"`). Поскольку внешний машинный код не проверяется анализатором AMA, действуют строгие пограничные правила:

### 11.1. Контракт блока `unsafe`

1. Объявление внешней функции не требует `unsafe`, но **любой вызов** функции `extern "C"`, разыменование сырого указателя (`*const T`, `*mut T`) или обращение к `extern static` обязаны находиться внутри блока `unsafe { ... }` (иначе ошибка **`E0601: call to extern function requires unsafe block`**).
2. Блок `unsafe` **не отключает** проверки AMA (`read`, `write`, `take`, CTFP) для обычных переменных APS внутри этого блока! Он лишь открывает доступ к 4 низкоуровневым операциям:
   - Вызов `unsafe fn` или `extern "C" fn`.
   - Разыменование сырых указателей `*const T` и `*mut T`.
   - Чтение и запись полей низкоуровневых объединений `union`.
   - Вызов ассемблерных вставок `asm!`.

### 11.2. Передача памяти через границу C ABI

1. **Заимствованная передача (`Borrowed FFI Pass`):**
   - Из `read Slice<T>` можно получить `*const T` через `.as_ptr()` и длину `.len()`. Владение остаётся у APS, переменная считается заимствованной по `read` на всё время вызова C-функции.
   - Из `write Slice<T>` можно получить `*mut T` через `.as_mut_ptr()`.
2. **Передача владения в C (`Into Raw`):**
   - Чтобы передать буфер в C-функцию, которая сама освободит его (или сохранит навсегда), используется `Box::into_raw(take boxed_val)`. Это переводит объект из-под контроля CTFP в сырой указатель, предотвращая двойное освобождение (`Double Free`).
3. **Приём владения из C (`From Raw`):**
   - Запрещено оборачивать указатель, выделенный чужим аллокатором (например, `malloc` из `msvcrt.dll`), напрямую в `Box::from_raw`, если аллокаторы не совпадают (**`E0604`** / нарушение контракта аллокатора). Для внешних ресурсов создаётся структура-обёртка с методом `fn drop(write self)`, вызывающим соответствующую C-функцию освобождения (например, `c_library_free(self.raw_ptr)`).

## 12. Обработка исключительных путей выполнения (`Result`, `?`, `defer`, `panic`)

В языке APS отсутствуют скрытые исключения (C++/Java-style exceptions). Все ожидаемые ошибки моделируются явно через возвращаемый тип `Result<T, E>`, а фатальные нарушения инвариантов — через механизм контролируемой паники (`panic`).

### 12.1. Оператор проброса ошибки `?` и освобождение ресурсов

При выполнении выражения `let data = read_packet(read socket)?`:
1. Если результат равен `Ok(val)`, значение `val` извлекается и связывается с `data`.
2. Если результат равен `Err(err)`, оператор `?` инициирует ранний выход из текущей функции.
3. Перед выполнением инструкции `ret` компилятор по таблице CTFP детерминированно вызывает деструкторы для всех локальных объектов, которые были созданы до точки `?` и находятся в состоянии `Owned(Valid)`, в обратном порядке их объявления. Ни один байт памяти и ни один открытый сокет не теряются.

### 12.2. Конструкция `defer` и её взаимодействие с CTFP

Блок `defer { ... }` позволяет запланировать выполнение произвольного кода очистки при выходе из текущей лексической области видимости:
- Инструкции `defer` выполняются по принципу стека (LIFO) перед автоматическими деструкторами переменных, объявленных до `defer`, которые этот `defer`-блок использует.
- Анализатор AMA проверяет, что код внутри `defer` не использует переменные, которые были перемещены (`take`) в основном теле функции до точки выхода (**`E0205: variable used in defer block may be moved before scope exit`**).

### 12.3. Поведение при `panic(...)`

Вызов `panic("message")` или аппаратно-программная ловушка (выход за границы массива `R0001`, деление на ноль `R0002`) инициирует аварийное завершение текущей задачи или потока:
- В режиме по умолчанию (`unwind = "deterministic"`): рантайм проходит по таблице деструкторов активных кадров текущего потока/задачи, освобождая внешние ресурсы и разблокируя мьютексы (с установкой флага `Poisoned`), после чего завершает поток или задачу с отчётом трассировки стека.
- В режиме жёсткого реального времени (`panic = "abort"`): процесс немедленно завершается после вывода диагностического дампа `R0xxx` без раскрутки стека.

#### Пример 8: Уровень 3 (`region`) — Пакетная аллокация $O(1)$ и циклический граф через `RegionHandle<T>`

```aps
struct DfaState {
    id: u32,
    is_accepting: bool,
    transitions: Vec<RegionHandle<DfaState>>
}

fn simulate_automaton(input: read Slice<u8>) -> bool {
    var accepted = false
    region dfa_arena {
        let s0 = dfa_arena.alloc(DfaState { id: 0, is_accepting: false, transitions: Vec::new() })
        let s1 = dfa_arena.alloc(DfaState { id: 1, is_accepting: true, transitions: Vec::new() })

        // Формируем цикл переходов s0 <-> s1 внутри региона `dfa_arena`:
        dfa_arena.get_write(s0).transitions.push(s1)
        dfa_arena.get_write(s1).transitions.push(s0)

        var current = s0
        for byte in input {
            let next_list = read dfa_arena.get_read(current).transitions
            current = next_list[0]
        }
        // Результат типа `bool` (Copy) безопасно покидает регион:
        accepted = dfa_arena.get_read(current).is_accepting
    } // Вся память состояний DFA освобождается за O(1) одной инструкцией сброса курсора!
    return accepted
}
```
**Гарантия AMA:** Циклический граф состояний создан без `unsafe` и без сборщика мусора, а его освобождение не требует обхода вершин и выполняется за $O(1)$.

#### Пример 9: Уровень 4 (`Shared<T>` и `share(...)`) — Потокобезопасное разделение конфигурации

```aps
struct RoutingTable {
    version: u64,
    routes: Vec<String>
}

fn main() {
    var builder = RoutingTable { version: 42, routes: Vec::new() }
    builder.routes.push(String::from("/api/v1/health"))
    builder.routes.push(String::from("/api/v1/metrics"))

    // Замораживаем объект и переводим его на Уровень 4 (Shared Immutable Memory):
    let shared_table: Shared<RoutingTable> = share(take builder)

    var workers = Vec::new()
    for worker_id in 0..4 {
        let table_ref = shared_table.clone() // Атомарный инкремент счётчика ссылок
        workers.push(thread::spawn(move || {
            println_u64(table_ref.version + worker_id)
            assert(table_ref.routes.len() == 2)
        }))
    }
    for w in take workers {
        w.join()
    }
}
```
**Гарантия AMA:** После вызова `share(take builder)` таблица маршрутизации становится глубоко неизменяемой; четыре потока читают её параллельно без блокировок и без малейшего риска гонки данных.

#### Пример 10: Разрыв циклов владения на Уровне 4 через `Shared<T>` и `Weak<T>`

```aps
struct TreeNode {
    name: String,
    parent: Option<Weak<TreeNode>>
}

fn main() {
    let root: Shared<TreeNode> = share(TreeNode {
        name: String::from("root"),
        parent: None
    })

    let child: Shared<TreeNode> = share(TreeNode {
        name: String::from("leaf_01"),
        parent: Some(Shared::downgrade(read root))
    })

    // Безопасный доступ к родителю через `.upgrade()`:
    match child.parent {
        Some(weak_parent) => {
            match weak_parent.upgrade() {
                Some(strong_parent) => assert(strong_parent.name == "root"),
                None => panic("parent already deallocated")
            }
        },
        None => {}
    }
}
```
**Гарантия AMA:** Слабая ссылка `Weak<TreeNode>` не увеличивает сильный счётчик ссылок `root`, поэтому при выходе `root` из области видимости память родителя гарантированно освобождается, а последующий вызов `weak_parent.upgrade()` безопасно вернёт `None`.

#### Пример 11: Структурный параллелизм (`task_scope`) с безопасным заимствованием локальных данных

```aps
async fn parallel_hash_blocks(
    read salt: Vec<u8>,
    write out_left: u64,
    write out_right: u64
) {
    await task_scope |scope| {
        scope.spawn(async {
            // Захват `salt` по `read` и `out_left` по `write`:
            *out_left = hash_with_salt(read salt, 1)
        })
        scope.spawn(async {
            // Захват того же `salt` по `read` и дизъюнктного `out_right` по `write`:
            *out_right = hash_with_salt(read salt, 2)
        })
    } // Барьер синхронизации: обе задачи гарантированно завершились до выхода из `parallel_hash_blocks`
}
```
**Гарантия AMA:** Благодаря барьеру `task_scope` асинхронные задачи работают с локальными ссылками без клонирования вектора `salt` и без оборачивания в `Shared<Mutex<...>>`.

#### Пример 12: Детерминированный порядок деструкторов при раннем выходе через `?` и `defer`

```aps
fn process_transaction(path: read str) -> Result<u64, IoError> {
    let conn = DbConnection::open("local_db")? // Освободится последним
    defer {
        audit_log("transaction scope exited")  // Выполнится перед деструктором `conn`
    }
    let temp_buffer = ByteBuffer::allocate(65536) // Освободится первым при выходе по `?`
    let bytes_read = fs::read_into(path, write temp_buffer)? // При ошибке `Err` здесь:
    // 1. Уничтожается `temp_buffer`
    // 2. Выполняется блок `defer`
    // 3. Закрывается `conn`
    return Ok(bytes_read as u64)
}
```
**Гарантия AMA:** Независимо от того, завершилась ли функция успешно (`Ok`) или прервалась на операторе `?` (`Err`), все локальные ресурсы и буферы освобождаются в строго детерминированном порядке LIFO.

#### Пример 13: Попытка модификации объекта через право только для чтения (`E0042`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/billing.aps
   struct DriverAccount {
       id: u64,
       balance: i64
   }

   fn apply_bonus(read driver: DriverAccount) {
       driver.balance += 100
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Вызывающая сторона передала объект с контрактом неизменяемости `read DriverAccount`, рассчитывая на сохранение инвариантов данных (например, при одновременном чтении того же объекта из других функций, итерации по коллекции или размещении объекта в памяти только для чтения `.rodata` / `Shared<T>`). Нарушение контракта `read` разрушает локальное рассуждение о коде, ломает оптимизации кэширования значений в регистрах (CSE / Load Elimination) и приводит к гонкам данных при параллельном чтении.
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Capability Pass** (проверка соответствия операции присваивания `+=` праву доступа базового пути `driver`).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0042]: cannot modify a read-only value
    --> src/billing.aps:8:5
     |
   7 | fn apply_bonus(read driver: DriverAccount) {
     |                ----------- `driver` is passed with `read` capability here
   8 |     driver.balance += 100
     |     ^^^^^^^^^^^^^^^^^^^^^ cannot mutate field `balance` through a `read` capability
     |
     = note: `read` parameters grant shared immutable access only
     = help: change the parameter signature to `write driver: DriverAccount` if mutation is intended
   ```
5. **Как исправить код:**
   ```aps
   struct DriverAccount {
       id: u64,
       balance: i64
   }

   fn apply_bonus(write driver: DriverAccount) {
       driver.balance += 100
   }

   fn main() {
       var driver = DriverAccount { id: 1, balance: 500 }
       apply_bonus(write driver)
       assert(driver.balance == 600)
   }
   ```

#### Пример 14: Использование переменной после передачи владения — Use-After-Move (`E0301`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/network.aps
   fn send_packet(take payload: Vec<u8>) {
       // пакет отправлен и буфер освобождён внутри send_packet
   }

   fn transmit() {
       let packet = vec![0xDE, 0xAD, 0xBE, 0xEF]
       send_packet(take packet)
       println_usize(packet.len())
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Функция `send_packet` приняла владение буфером `packet` через `take` и по окончании своей работы вызвала деструктор, вернув страницы памяти в системный аллокатор. Повторное чтение `packet` в `transmit()` обратилось бы к уже освобождённой куче (**Use-After-Free**) или вызвало бы повторный вызов деструктора в конце `transmit()` (**Double Free**), что ведёт к повреждению метаданных аллокатора и возможности выполнения произвольного кода (RCE).
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Liveness & Move Pass** (проверка состояния вершины `packet` в графе OLG: состояние равно `Moved`).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0301]: use of moved value `packet`
    --> src/network.aps:9:19
     |
   7 |     let packet = vec![0xDE, 0xAD, 0xBE, 0xEF]
     |         ------ move occurs because `packet` has type `Vec<u8>`, which does not implement `Copy`
   8 |     send_packet(take packet)
     |                 ----------- ownership of `packet` was transferred (`take`) here
   9 |     println_usize(packet.len())
     |                   ^^^^^^ value used here after ownership transfer
     |
     = help: read the length before transferring ownership, or change `send_packet` to accept `read Vec<u8>`
   ```
5. **Как исправить код:**
   ```aps
   fn send_packet(read payload: Vec<u8>) {
       // Читаем и отправляем байты без захвата владения
   }

   fn transmit() {
       let packet = vec![0xDE, 0xAD, 0xBE, 0xEF]
       send_packet(read packet)
       println_usize(packet.len())
   }
   ```

#### Пример 15: Двойная передача владения в одном вызове — Double Move (`E0201`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/merger.aps
   fn merge_buffers(take left: String, take right: String) -> String {
       var out = left
       out.push_str(read right)
       return out
   }

   fn run() {
       let text = String::from("APS")
       let combined = merge_buffers(take text, take text)
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Если один и тот же кучный буфер будет передан по значению в оба параметра `left` и `right`, внутри `merge_buffers` возникнут два независимых владельца одного адреса памяти (`Aliased Unique Ownership`). При реаллокации `out.push_str(read right)` буфер `left` может быть освобождён, пока из `right` идёт чтение (`memcpy` из освобождённой памяти), а при выходе из `merge_buffers` деструктор `right` освободит уже невалидный указатель.
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Liveness & Move Pass** (при анализе аргументов вызова слева направо первый `take text` переводит `text` в `Moved`).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0201]: cannot transfer ownership of `text` more than once
    --> src/merger.aps:10:45
     |
   10 |     let combined = merge_buffers(take text, take text)
     |                                  ---------  ^^^^^^^^^ second ownership transfer of `text` occurs here
     |                                  |
     |                                  first ownership transfer occurs here
     |
     = help: explicitly clone the value with `take text.clone()` if two independent buffers are required
   ```
5. **Как исправить код:**
   ```aps
   fn run() {
       let text = String::from("APS")
       let combined = merge_buffers(take text.clone(), take text)
       assert(combined == "APSAPS")
   }
   ```

#### Пример 16: Конфликт одновременного чтения и записи (`read` + `write` Aliasing — `E0040`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/ledger.aps
   fn transfer_self(read src: Vec<i64>, write dst: Vec<i64>) {
       for item in src {
           dst.push(item)
       }
   }

   fn process() {
       var entries = vec![10, 20, 30]
       transfer_self(read entries, write entries)
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Классическая уязвимость **Iterator Invalidation / Use-After-Realloc**: цикл `for item in src` удерживает указатель на внутренний буфер вектора в куче. Вызов `dst.push(item)` через алиас `dst` (указывающий на тот же вектор `entries`) при превышении ёмкости (`capacity`) выделяет новый блок памяти и **освобождает старый буфер**, по которому прямо в этот момент итерируется `src`. Следующая итерация цикла читает освобождённую память.
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Capability Pass** (проверка инварианта `Aliasing XOR Mutability` на множестве активных заимствований $\Delta$).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0040]: cannot borrow `entries` as `write` because it is already borrowed as `read`
    --> src/ledger.aps:10:33
     |
   10 |     transfer_self(read entries, write entries)
     |                   ------------  ^^^^^^^^^^^^^ mutable (`write`) borrow occurs here
     |                   |
     |                   immutable (`read`) borrow occurs here
     |
     = note: AMA prohibits simultaneous `read` and `write` capabilities to the same memory path
     = help: clone the source data or collect changes into a separate buffer before mutating `entries`
   ```
5. **Как исправить код:**
   ```aps
   fn duplicate_entries(write dst: Vec<i64>) {
       let snapshot = dst.clone()
       for item in read snapshot {
           dst.push(item)
       }
   }

   fn process() {
       var entries = vec![10, 20, 30]
       duplicate_entries(write entries)
   }
   ```

#### Пример 17: Два одновременных эксклюзивных права на запись (`write` + `write` Conflict — `E0041`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/swap.aps
   fn mix_buffers(write a: Vec<u8>, write b: Vec<u8>) {
       a.push(1)
       b.push(2)
   }

   fn run() {
       var buf = vec![0]
       mix_buffers(write buf, write buf)
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Функция `mix_buffers` скомпилирована в предположении (`noalias` в LLVM IR), что указатели `a` и `b` никогда не перекрываются. Оптимизатор LLVM кэширует поля `a.len` и `b.len` в разных регистрах процессора. Передача одного и того же объекта в оба параметра `write` приводит к нарушению контракта `noalias`, перезаписи длины вектора устаревшим значением из регистра и разрушению кучи при реаллокации.
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Capability Pass** (обнаружение двух пересекающихся заимствований `write` для пути `buf`).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0041]: cannot borrow `buf` as `write` more than once at a time
    --> src/swap.aps:9:28
     |
   9 |     mix_buffers(write buf, write buf)
     |                 ---------  ^^^^^^^^^ second `write` borrow occurs here
     |                 |
     |                 first `write` borrow occurs here
     |
     = help: pass distinct variables or use `split_at_write` if operating on non-overlapping slices
   ```
5. **Как исправить код:**
   ```aps
   fn run() {
       var buf_a = vec![0]
       var buf_b = vec![0]
       mix_buffers(write buf_a, write buf_b)
   }
   ```

#### Пример 18: Побег ссылки/дескриптора за пределы блока `region` — Region Escape (`E0305`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/parser_arena.aps
   struct AstNode {
       token_id: u32
   }

   fn parse_expr() -> RegionHandle<AstNode> {
       region ast_mem {
           let root = ast_mem.alloc(AstNode { token_id: 7 })
           return root
       }
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   При выходе из блока `region ast_mem` вся память арены мгновенно сбрасывается и возвращается пулу страниц рантайма. Если дескриптор `root` покинет блок `region`, вызывающий код получит висячий дескриптор (**Dangling Region Handle**), указывающий на освобождённую или уже переиспользованную другим регионом память.
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Region Escape Pass** (проверка тега региона $\rho_{\text{ast\_mem}}$ в возвращаемом типе и внешних присваиваниях).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0305]: region-allocated handle `root` cannot escape `region ast_mem`
    --> src/parser_arena.aps:9:16
     |
   7 |     region ast_mem {
     |            ------- `ast_mem` region lifetime begins here
   8 |         let root = ast_mem.alloc(AstNode { token_id: 7 })
   9 |         return root
     |                ^^^^ `root` escapes the `region` block here
   10|     }
     |     - `ast_mem` is deallocated in bulk at the end of this block
     |
     = help: extract a self-contained value (such as `u32` or an owned `struct`) before exiting `region ast_mem`
   ```
5. **Как исправить код:**
   ```aps
   fn parse_expr() -> u32 {
       region ast_mem {
           let root = ast_mem.alloc(AstNode { token_id: 7 })
           return ast_mem.get_read(root).token_id
       }
   }
   ```

#### Пример 19: Сохранение ссылки региона во внешней переменной (`E0305`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/region_leak.aps
   fn process_request() {
       var escaped_handle: Option<RegionHandle<String>> = None
       region req_arena {
           let h = req_arena.alloc(String::from("temporary_header"))
           escaped_handle = Some(h)
       }
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Переменная `escaped_handle` объявлена во внешней области видимости функций ($\mathcal{L}(\text{escaped\_handle}) \sqsupset \mathcal{L}(\text{req\_arena})$). Запись туда дескриптора `h` из вложенного региона нарушает инвариант вложенности времён жизни $\mathcal{L}(\ell) \subseteq \mathcal{L}(r_{\text{src}})$, делая `escaped_handle` недействительным сразу после закрывающей скобки `region req_arena`.
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Region Escape Pass** (проверка ограничения $\text{RegionTag}(\text{lhs}) \sqsubseteq \text{RegionTag}(\text{rhs})$ при присваивании).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0305]: value tied to `region req_arena` cannot be assigned to outer variable `escaped_handle`
    --> src/region_leak.aps:6:9
     |
   3 |     var escaped_handle: Option<RegionHandle<String>> = None
     |         -------------- outer variable declared here (outlives `req_arena`)
   4 |     region req_arena {
   5 |         let h = req_arena.alloc(String::from("temporary_header"))
   6 |         escaped_handle = Some(h)
     |         ^^^^^^^^^^^^^^^^^^^^^^^^ `h` escapes `region req_arena` via assignment
   7 |     }
     |     - `region req_arena` ends here, invalidating `h`
     |
     = help: move `escaped_handle` inside `region req_arena` or clone the owned `String` before exiting the region
   ```
5. **Как исправить код:**
   ```aps
   fn process_request() {
       var extracted_header: Option<String> = None
       region req_arena {
           let h = req_arena.alloc(String::from("temporary_header"))
           extracted_header = Some(req_arena.get_read(h).clone())
       }
       assert(extracted_header.is_some())
   }
   ```

#### Пример 20: Использование `RegionHandle` с чужим регионом (`E0306`)

1. **Пример APS-кода:**

   ```aps
   fn cross_lookup() {
   ```

#### Пример 24: Перемещение значения (`take`) во время активного заимствования `read` (`E0203`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/move_while_borrowed.aps
   fn consume_string(take s: String) {}

   fn inspect() {
       let message = String::from("critical_alert")
       let slice_view: read str = message.as_str()
       consume_string(take message)
       println(slice_view)
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Переменная `slice_view` удерживает невладеющий указатель `(ptr, len)` на внутренний буфер строки `message`. Когда `consume_string(take message)` забирает владение `message` и уничтожает строку, буфер в куче освобождается. Последующий вызов `println(slice_view)` читает память по висячему указателю (**Use-After-Free via Active Slice**).
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Liveness & Move Pass** (проверка отсутствия активных заимствований в $\Delta(\text{message})$ в момент операции `take message`, пока `slice_view` жив по NLL).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0203]: cannot move out of `message` because it is currently borrowed as `read`
    --> src/move_while_borrowed.aps:7:20
     |
   6 |     let slice_view: read str = message.as_str()
     |                                ------- `message` is borrowed as `read` here
   7 |     consume_string(take message)
     |                    ^^^^^^^^^^^^ move out of `message` occurs here while borrow is still active
   8 |     println(slice_view)
     |             ---------- `read` borrow is later used here
     |
     = help: finish using `slice_view` before transferring ownership of `message` with `take`
   ```
5. **Как исправить код:**
   ```aps
   fn inspect() {
       let message = String::from("critical_alert")
       let slice_view: read str = message.as_str()
       println(slice_view) // Последнее использование заимствования `slice_view` (NLL завершает заимствование)
       consume_string(take message) // Теперь перемещение абсолютно безопасно!
   }
   ```

#### Пример 25: Использование переменной после условного перемещения в одной ветке `if` (`E0202`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/branch_move.aps
   fn archive(take data: Vec<u8>) {}

   fn handle_payload(should_archive: bool) {
       let payload = vec![1, 2, 3, 4]
       if should_archive {
           archive(take payload)
       }
       println_usize(payload.len())
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Если `should_archive == true`, буфер `payload` уже передан в `archive` и освобождён. В точке слияния после `if` переменная находится в состоянии `MaybeMoved`. Безусловное чтение `payload.len()` при `should_archive == true` приведёт к чтению освобождённой памяти.
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Liveness & Move Pass** (анализ решетки состояний на Join Point в MIR CFG: $\text{Moved} \sqcup \text{Owned(Valid)} = \text{MaybeMoved}$).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0202]: use of possibly moved value `payload`
    --> src/branch_move.aps:9:19
     |
   5 |     let payload = vec![1, 2, 3, 4]
     |         ------- move occurs because `payload` has type `Vec<u8>`, which does not implement `Copy`
   6 |     if should_archive {
   7 |         archive(take payload)
     |                 ------------ value moved here in `then` branch
   8 |     }
   9 |     println_usize(payload.len())
     |                   ^^^^^^^ value used here after potential move
     |
     = help: read `payload.len()` before the `if` statement, or pass `read payload` into `archive`
   ```
5. **Как исправить код:**
   ```aps
   fn handle_payload(should_archive: bool) {
       let payload = vec![1, 2, 3, 4]
       let len = payload.len()
       if should_archive {
           archive(take payload)
       }
       println_usize(len)
   }
   ```

#### Пример 26: Перемещение поля структуры и последующее обращение ко всей структуре — Partial Move (`E0204`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/partial_move.aps
   struct Connection {
       host: String,
       token: String
   }

   fn consume_Connection(take c: Connection) {}

   fn start() {
       let conn = Connection {
           host: String::from("10.0.0.1"),
           token: String::from("secret_jwt")
       }
       let extracted_token = take conn.token
       consume_Connection(take conn)
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   После перемещения `take conn.token` структура `conn` переходит в состояние `PartiallyMoved({token})`: поле `conn.host` ещё валидно, но поле `conn.token` уже перемещено во внешний владелец `extracted_token`. Если передать всю структуру `conn` в `consume_Connection`, деструктор `Connection` попытается освободить как `host`, так и уже перемещённый `token` (**Double Free поля структуры**).
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Liveness & Move Pass** (отслеживание битовой маски инициализации полей структуры `PartiallyMoved`).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0204]: cannot move `conn` because its field `conn.token` was already moved
    --> src/partial_move.aps:15:24
     |
   14 |     let extracted_token = take conn.token
     |                           --------------- field `conn.token` moved here
   15 |     consume_Connection(take conn)
     |                        ^^^^^^^^^ cannot transfer whole struct `conn` after partial move
     |
     = note: field `conn.host` remains valid and can still be accessed or moved individually
     = help: clone `conn.token` instead of moving it, or reassign `conn.token` before moving `conn`
   ```
5. **Как исправить код:**
   ```aps
   fn start() {
       var conn = Connection {
           host: String::from("10.0.0.1"),
           token: String::from("secret_jwt")
       }
       let extracted_token = take conn.token
       conn.token = String::from("redacted") // Восстанавливаем полную инициализацию `conn`
       consume_Connection(take conn)
       println(read extracted_token)
   }
   ```

#### Пример 27: Захват локальной ссылки `read` в отсоединённую асинхронную задачу (`E0401`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/async_escape.aps
   async fn launch_background_worker() {
       let local_buffer = vec![10, 20, 30, 40]
       async::spawn_detached(async {
           println_usize(local_buffer.len())
       })
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Функция `async::spawn_detached` ставит задачу в глобальный планировщик и немедленно возвращает управление, не дожидаясь её завершения. Функция `launch_background_worker` завершается и уничтожает `local_buffer` по правилам CTFP, в то время как фоновая задача на другом рабочем потоке планировщика просыпается позже и читает уже уничтоженный `local_buffer` (**Async Use-After-Free**).
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Concurrency Pass** (проверка захватов замыкания для `spawn_detached`: запрещены любые невладеющие ссылки `read`/`write` на локальный кадр).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0401]: borrowed value `local_buffer` does not live long enough for detached async task
    --> src/async_escape.aps:4:27
     |
   3 |     let local_buffer = vec![10, 20, 30, 40]
     |         ------------ `local_buffer` is owned by `launch_background_worker`
   4 |     async::spawn_detached(async {
     |  ___________________________^
   5 | |         println_usize(local_buffer.len())
     | |                       ------------ captured as `read` inside detached task here
   6 | |     })
     | |_____^ detached task may outlive the current function frame
   7 | }
     | - `local_buffer` is deallocated here when `launch_background_worker` returns
     |
     = help: use structured concurrency (`task_scope`) or transfer ownership into the task with `async move` / `Shared<T>`
   ```
5. **Как исправить код:**
   ```aps
   async fn launch_background_worker() {
       let local_buffer = vec![10, 20, 30, 40]
       async::spawn_detached(async move {
           // Владение `local_buffer` перемещено внутрь задачи:
           println_usize(local_buffer.len())
       })
   }
   ```

#### Пример 28: Одновременный захват `write` одной переменной двумя задачами в `task_scope` (`E0402`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/race_scope.aps
   async fn concurrent_increment() {
       var counter: i64 = 0
       await task_scope |scope| {
           scope.spawn(async {
               counter += 1
           })
           scope.spawn(async {
               counter += 2
           })
       }
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Две задачи внутри `task_scope` могут выполняться параллельно на разных физических ядрах многопоточного ворк-стилинг планировщика APS. Несинхронизированная операция `counter += 1` (Read-Modify-Write) из двух потоков порождает классическую гонку данных (**Data Race**) и потерю обновлений.
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Concurrency Pass & Capability Pass** (обнаружение двух одновременных захватов `write counter`, чьи времена жизни перекрываются на протяжении всего `task_scope`).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0402]: cannot capture `counter` as `write` in multiple concurrent tasks within `task_scope`
    --> src/race_scope.aps:8:21
     |
   5 |         scope.spawn(async {
     |                     ----- first `write` capture of `counter` occurs in this task
   6 |             counter += 1
   7 |         })
   8 |         scope.spawn(async {
     |                     ^^^^^ second concurrent `write` capture of `counter` occurs here
   9 |             counter += 2
     |             ------- conflicting mutable access to `counter`
     |
     = help: use `AtomicI64` for lock-free concurrent updates or compute partial results separately and sum after `task_scope`
   ```
5. **Как исправить код:**
   ```aps
   async fn concurrent_increment() {
       let counter = AtomicI64::new(0)
       await task_scope |scope| {
           scope.spawn(async {
               counter.fetch_add(1, MemoryOrder::SeqCst)
           })
           scope.spawn(async {
               counter.fetch_add(2, MemoryOrder::SeqCst)
           })
       }
       assert(counter.load(MemoryOrder::SeqCst) == 3)
   }
   ```

#### Пример 29: Передача несинхронизированного дескриптора региона `RegionHandle<T>` в другой поток (`E0404`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/region_thread.aps
   fn bad_threading() {
       region local_arena {
           let h = local_arena.alloc(String::from("thread_unsafe"))
           let worker = thread::spawn(move || {
               println_u32(h.raw_index())
           })

       }
   ```

2. **Почему он опасен (технический разбор угрозы):**

Кроме того, отсоединённый поток `thread::spawn` не привязан статически к времени жизни `region local_arena`. Передача `RegionHandle` в другой поток нарушает потоковую изоляцию региона.
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Concurrency Pass** (проверка ограничения `T: Send` для всех переменных, перемещаемых в `thread::spawn`: `RegionHandle<T>` не реализует `Send`).

   ```text
    --> src/region_thread.aps:5:22
     |
   4 |         let h = local_arena.alloc(String::from("thread_unsafe"))
     |             - `h` has type `RegionHandle<String>`, which is tied to thread-local `region local_arena`
   5 |         let worker = thread::spawn(move || {
     |                      ^^^^^^^^^^^^^ `RegionHandle<String>` cannot cross thread boundaries
     |
     = note: `region` arenas use thread-local lock-free bump allocation and cannot be accessed from other threads
     = help: convert the data into an owned type or freeze it with `share(...)` (`Shared<T>`) before spawning threads
   ```
5. **Как исправить код:**
   ```aps
   fn good_threading() {
       let shared_msg: Shared<String> = share(String::from("thread_safe"))
       let worker = thread::spawn(move || {
           println(read shared_msg)
       })
       worker.join()
   }
   ```

#### Пример 30: Побег ссылки из-под охраны мьютекса (`MutexGuard` Lifetime Escape — `E0304`)

1. **Пример APS-кода:**
   ```aps
   // Файл: src/mutex_escape.aps
   fn extract_unlocked_ref(mtx: read Mutex<Vec<i32>>) -> read Vec<i32> {
       let guard = mtx.lock()
       return guard.as_read()
   }
   ```
2. **Почему он опасен (технический разбор угрозы):**
   Охранный объект `guard` (`MutexGuard<Vec<i32>>`) удерживает мьютекс заблокированным только до тех пор, пока сам `guard` жив. При выходе из `extract_unlocked_ref` деструктор `guard` автоматически **разблокирует мьютекс**. Если бы ссылка `read Vec<i32>` пережила `guard`, вызывающий код читал бы и модифицировал данные уже без защиты мьютекса параллельно с другими потоками (**Data Race after Unlock**).
3. **На каком этапе компилятор обнаруживает проблему:**
   **AMA Lifetime Analysis** (происхождение возвращаемой ссылки `guard.as_read()` привязано к локальному владельцу `guard`, который уничтожается в конце функции).
4. **Точное сообщение об ошибке компилятора:**
   ```text
   error[E0304]: cannot return reference to data guarded by local `MutexGuard` `guard`
    --> src/mutex_escape.aps:4:12
     |
   3 |     let guard = mtx.lock()
     |         ----- `MutexGuard` acquired here
   4 |     return guard.as_read()
     |            ^^^^^^^^^^^^^^^ borrows data whose lock is released at the end of this function
   5 | }
     | - `guard` is dropped here, unlocking `mtx` and invalidating any references derived from it
     |
     = help: perform the read operation while holding `guard` or return a cloned value before unlocking
   ```
5. **Как исправить код:**
   ```aps
   fn extract_cloned_snapshot(mtx: read Mutex<Vec<i32>>) -> Vec<i32> {
       let guard = mtx.lock()
       return guard.as_read().clone()
   }
   ```

#### Пример 31: Вызов функции `extern "C"` и разыменование сырого указателя вне блока `unsafe` (`E0601`)

1. **Пример APS-кода:**

   ```text
     |

     |            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ call to foreign C ABI function outside `unsafe` block
     |
     = note: foreign functions bypass AMA static memory verification; the caller must uphold pointer validity invariants
     = help: wrap the call in `unsafe { ... }` after verifying that `buf.as_ptr()` and `buf.len()` match the C contract
   ```
5. **Как исправить код:**
   ```aps
   extern "C" {

           return c_crc32_compute(buf.as_ptr(), buf.len())
       }
   }
   ```

## 14. Резюме инвариантов безопасности AMA

Архитектура памяти **AMA (APS Adaptive Memory Architecture)** обеспечивает математически строгую защиту от всех классов ошибок работы с памятью в безопасном подмножестве языка APS:

| Класс уязвимости памяти | Механизм предотвращения в AMA | Коды диагностик |
| :--- | :--- | :--- |
| **Use-After-Free / Use-After-Move** | Граф OLG + отслеживание состояния `Moved` / `PartiallyMoved` | `E0201`–`E0205`, `E0301` |
| **Double Free** | Единственный владелец (`own T`) + детерминированный CTFP | `E0201`, `E0204` |
| **Dangling Stack / Guard Reference** | Запрет возврата ссылок на локальных владельцев | `E0302`, `E0304` |
| **Region Escape / Arena UAF** | Фантомная типизация регионов $\rho_r$ и проверка невыхода | `E0305`, `E0306` |
| **Unintended Mutation / Aliasing Bug** | Права доступа второго класса `read` / `write` (`Aliasing XOR Mutability`) | `E0040`–`E0045` |
| **Data Races в потоках и `async`** | Заморозка `Shared<T>`, `task_scope` и проверка `Send` / `Sync` | `E0401`–`E0405` |
| **Неконтролируемый доступ к C ABI** | Обязательная изоляция в блоках `unsafe` | `E0601`–`E0605` |
| **Выход за границы массива / Деление на 0** | Статический анализ диапазонов + рантайм-ловушки | `R0001`, `R0002` |
